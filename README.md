# COOKLY

Cookly помогает решить, что приготовить из продуктов, которые уже есть дома. Добавьте продукты, при желании ограничьте время и получите до пяти подходящих блюд с подробными рецептами. В каталоге — 48 домашних рецептов на русском языке.

Это статический MVP на React, TypeScript, Vite и React Router. Основной сценарий не требует аккаунта, сервера, базы данных или AI API. Отправка продуктовых событий в PostHog подключается отдельно и остается выключенной без корректной конфигурации и согласия посетителя.

## Локальный запуск

Понадобятся Node.js **22.12 или новее**, npm и Git. Все команды выполняются в папке проекта.

```sh
npm install
npm run dev
```

Откройте адрес, который покажет Vite в терминале, обычно `http://localhost:5173`. Остановить сервер можно сочетанием `Ctrl+C`.

```sh
# Проверить логику приложения
npm run test

# Проверить TypeScript и собрать production-версию
npm run build

# Посмотреть собранный сайт локально
npm run preview
```

Готовые файлы находятся в `dist/`. Сервер preview обычно доступен по адресу `http://localhost:4173`; он предназначен для локальной проверки сборки. В CI используется `npm ci`, поэтому `package-lock.json` нужно хранить в Git вместе с `package.json`.

## Что реализовано

- Ввод продуктов с клавиатуры, быстрые подсказки, удаление и очистка списка, защита от повторов.
- Необязательный лимит времени: 20, 30, 45 или 60 минут.
- Подбор блюд по составу; карточки показывают совпадения и недостающие продукты.
- Подробный рецепт с количеством ингредиентов, порциями и шагами приготовления.
- Подтверждение «Буду готовить», состояние загрузки и понятные пустые состояния.
- Адаптивная верстка для телефона и компьютера, видимый фокус и доступные элементы управления.
- Отдельный холодильник с сохранением продуктов в localStorage; список для текущего поиска и лимит времени живут только до перезагрузки страницы.
- Единый сервис аналитики: локальный журнал для отладки и необязательная отправка обезличенных событий в PostHog Cloud.
- SVG-логотип, локальные данные и подготовленный workflow GitHub Pages.
- Профиль семьи без регистрации: размер семьи, дети, нелюбимые продукты, аллергии, тип питания и сложность.
- Умные замены отсутствующих продуктов с подсветкой варианта, который уже есть дома.
- Пересчёт ингредиентов на 1–6 порций с округлением штучных продуктов вверх.
- Cooking Mode с текущим шагом, таймером, навигацией назад/вперёд и полным списком шагов.
- Финальная оценка блюда 👍/👎 с сохранением в localStorage и влиянием на следующие рекомендации.

## Структура проекта

```text
src/
  components/       Повторно используемые элементы интерфейса
  pages/            Главная, рекомендации и страница рецепта
  data/             Каталог рецептов и справочник продуктов
  types/            Типы рецептов, ингредиентов и рекомендаций
  utils/            Нормализация, подбор и аналитика
  hooks/            Состояние продуктов, профиля и отзывов
  App.tsx           Маршруты приложения
public/             Статические файлы
.github/workflows/
  deploy.yml        Проверка, сборка и публикация в GitHub Pages
```

Данные, подбор и аналитика отделены от UI: можно расширять каталог или менять способ записи событий без переписывания экранов. `useProfile` хранит настройки семьи, `substitutions.ts` содержит логичные пары замен, `servings.ts` отвечает за масштабирование количеств, а Cooking Mode управляет пошаговой готовкой.

## Как работает подбор

Названия продуктов нормализуются: регистр, пробелы и распространенные варианты названий не должны создавать разные продукты. Для каждого рецепта определяется наличие ингредиентов и рассчитывается взвешенная доля совпадений. Основные продукты имеют больший вес, чем вспомогательные.

В первую очередь предлагаются блюда, для которых есть все обязательные продукты, затем блюда с одним и двумя недостающими продуктами. Остальные варианты дополняют выдачу при необходимости. Учитывается выбранное ограничение времени; случайного перемешивания нет. Если подходящих блюд мало, приложение показывает доступное количество, а не добавляет рецепты вне лимита.

Соль, перец, вода, масло и базовые специи считаются запасами кухни: их не требуется вводить. Это допущение MVP, а не проверка фактического наличия продуктов. Необязательные ингредиенты не должны мешать рекомендации блюда.

## Сохранение данных и продуктовая аналитика

### Локальные данные и сброс

Список продуктов в форме поиска и выбранный лимит времени намеренно хранятся только в памяти React: после перезагрузки страницы они сбрасываются. Постоянное состояние в `localStorage` включает `cookly:fridge` для отдельного холодильника, `cookly:profile` для профиля семьи, `cookly:feedback` для оценок, `cookly:recipe-usefulness` для ответов о достаточности рецепта и `cookly:analytics` для локальной истории событий. Согласие, код исследования и ручной QA-режим хранятся отдельно в `cookly:analytics:consent`, `cookly:analytics:participant` и `cookly:analytics:qa`.

Эти операции имеют разный результат:

- общий сброс данных Cookly очищает холодильник, профиль, код участника и локальную историю событий, но сохраняет выбор согласия и настройку QA;
- очистка локальной истории аналитики удаляет только записи из этого браузера;
- ни одна локальная операция не удаляет события, которые уже были отправлены в PostHog. Серверные данные удаляются отдельно пользователем с соответствующим доступом в PostHog.

Для ручного просмотра диагностической истории откройте DevTools → Console:

```js
JSON.parse(localStorage.getItem('cookly:analytics') || '[]')
```

### Подключение PostHog Cloud

1. Создайте проект в PostHog Cloud и откройте настройки проекта.
2. Скопируйте **Project API Key** с префиксом `phc_` и указанный для проекта ingestion host. Project API Key предназначен для клиентского SDK. Не используйте в браузере **Personal API Key**, ключ серверного API или другой приватный секрет: runtime и GitHub Actions отклоняют включенную конфигурацию, если ключ не соответствует формату `phc_…`.
3. Скопируйте `.env.example` в `.env.local` и заполните:

```dotenv
VITE_ANALYTICS_ENABLED=true
VITE_POSTHOG_KEY=phc_...
VITE_POSTHOG_HOST=https://eu.i.posthog.com
```

Host в примере подходит для EU Cloud только тогда, когда именно он указан в настройках проекта. Для другого региона используйте host из PostHog. После изменения `.env.local` перезапустите Vite. Не коммитьте `.env.local` и реальные значения в репозиторий.

При `VITE_ANALYTICS_ENABLED=false`, пустом ключе или некорректном host приложение продолжает работать без сетевой аналитики, а уведомление о ней не показывается. Session replay, autocapture и автоматический pageview в MVP отключены. При корректной конфигурации события не записываются ни в локальную историю, ни в PostHog до явного согласия посетителя; выбор можно изменить в настройках Cookly.

### События и безопасные свойства

Сервис регистрирует SPA-переходы как `page_view` и продуктовые события:

| Сценарий | События |
| --- | --- |
| Холодильник | `fridge_opened`, `fridge_item_added`, `fridge_item_removed`, `fridge_used_for_search` |
| Рекомендации | `recommendations_requested`, `recommendations_shown`, `recipe_opened` |
| Рецепт | `servings_selected`, `ingredient_substitution_selected`, `recipe_liked`, `recipe_disliked`, `recipe_usefulness_answered` |
| Магазин | `mock_store_opened`, `mock_checkout_completed` |
| Готовка | `cooking_started`, `cooking_step_changed`, `cooking_completed` |

Событие создается после действия пользователя или успешного завершения операции. Повторный рендер React и навигация по HashRouter не должны создавать дубль `page_view`.

Разрешенные свойства включают `path`, `device_type`, `referrer_host`, `recipe_id`, `recipe_category`, `cooking_time`, `number_of_servings`, `missing_ingredients_count`, `matched_ingredients_count`, `recommendation_position`, `search_source`, `total_recommendations`, `step_number`, `elapsed_time_ms`, `answer`, а также обезличенные признаки MVP-теста. `page_view.path` передается только как шаблон маршрута: `/`, `/fridge`, `/recipes`, `/recipe/:id`, `/cook/:id` или `/other`. Сырой URL, query/hash и фактический идентификатор из адреса в этом свойстве не отправляются.

Перед отправкой `before_send` повторно проверяет имя события и allowlist свойств. Из добавляемых SDK полей остаются только анонимные технические идентификаторы PostHog, необходимые для уникальных посетителей, сессий и дедупликации; автоматически добавленные URL, referrer, поисковые параметры и UTM-поля удаляются. Cookly не отправляет имена, телефоны, email, сырые списки продуктов, аллергии, медицинские ограничения и другие чувствительные сведения.

### Организованный MVP-тест

В настройках аналитики укажите участнику анонимный код вида `R01`, `R02`, `R03`. Не используйте имя, email или телефон. Код нормализуется в верхний регистр, сохраняется только для текущего теста и прикладывается к событиям как `participant_code`. Один код следует выдавать одному участнику и не переиспользовать.

Организатор также может выдать готовую ссылку, например `https://alikhan-35.github.io/cookly/?participant=R01#/`. Поддерживаются параметры `participant` и `participant_code`, как перед `#`, так и после маршрута HashRouter. Валидный код сохраняется в браузере, а сам служебный параметр удаляется из адресной строки до запуска аналитики.

Для собственных проверок включите там же режим QA или добавьте `?qa=1` перед `#` в адресе, например `https://alikhan-35.github.io/cookly/?qa=1#/`. Параметр `qa=1` сохраняет QA-режим, а `qa=0` снимает ранее сохраненную ручную настройку; оба значения удаляются из адресной строки до инициализации аналитики. На `localhost` и `127.0.0.1` QA включен автоматически независимо от параметра. Действия QA остаются в локальной истории с признаком `qa_mode = true` и не отправляются в PostHog.

В production dashboard используйте общие фильтры:

- `participant_code` задан — только организованный MVP-тест;
- `qa_mode` не равен `true` — дополнительная защита от тестовых сессий;
- при необходимости диапазон дат конкретной волны теста.

Главная гипотеза подтверждается только для участника, который открыл рецепт не позднее пяти минут после `recommendations_requested` (`recipe_opened.elapsed_time_ms <= 300000`) **и** ответил `yes` в `recipe_usefulness_answered`. Простое открытие рецепта успехом не считается. Цель MVP: не менее **70% уникальных тестовых участников** выполнили оба условия.

### Проверка событий

1. Запустите приложение с заполненным `.env.local`, примите уведомление об аналитике, задайте код `R01` и убедитесь, что QA-режим выключен.
2. Откройте холодильник, добавьте продукт, запросите рекомендации, откройте рецепт, ответьте на вопрос о достаточности рецепта, начните и завершите готовку, оставьте оценку и пройдите сценарий mock store.
3. В PostHog откройте **Activity / Live events** и отфильтруйте события по `participant_code = R01`. Проверьте названия, свойства, порядок и отсутствие дублей после обновления страницы.
4. Отдельно включите QA-режим и убедитесь, что события с `qa_mode = true` остаются в локальной истории, но не появляются в PostHog.

Production-сборка GitHub Pages настроена с реальным Project API Key и ingestion host PostHog US. После деплоя PostHog получил события `page_view` и `fridge_opened` из опубликованного сайта. Эти события помечены как автоматический трафик, поэтому проверка реального участника и остальных сценариев остается открытой; панель исключает автоматический трафик.

### Dashboard `COOKLY — MVP Analytics`

Защищенная панель [COOKLY — MVP Analytics](https://us.posthog.com/project/663130/dashboard/2210946) создана в PostHog и не опубликована для общего доступа. Она содержит 16 карточек по всем 13 показателям ниже и отдельную разбивку посещений по разделам. Каждая карточка исключает автоматический трафик; QA-события клиент не отправляет. Период по умолчанию — 30 дней. Показатели относятся только к посетителям, разрешившим аналитику, и не являются полным счетчиком всего трафика сайта.

| № | Insight | Настройка |
| --- | --- | --- |
| 1 | Unique visitors | SQL: уникальные `distinct_id` с `page_view` за 30 дней; отдельная карточка разбивает посещения по безопасному шаблону `path` |
| 2 | Sessions | Trend по `page_view`, агрегация unique sessions |
| 3 | Visits by device | Уникальные сессии `page_view` с breakdown по `device_type` |
| 4 | Traffic sources | Уникальные сессии `page_view` с breakdown по `referrer_host` |
| 5 | Recommendations requested | Количество `recommendations_requested` |
| 6 | Recipes opened | Количество `recipe_opened` |
| 7 | Cooking sessions started | Количество `cooking_started` |
| 8 | Cooking sessions completed | Количество `cooking_completed` |
| 9 | Positive and negative feedback | Две серии: `recipe_liked` и `recipe_disliked` |
| 10 | Fridge usage | Открытия `fridge_opened` и поиски `fridge_used_for_search` |
| 11 | Mock store interest | Открытия `mock_store_opened` и завершения `mock_checkout_completed` |
| 12 | Recipe selection time | Медиана и p90 свойства `recipe_opened.elapsed_time_ms` |
| 13 | MVP success rate | SQL/HogQL по уникальному `participant_code`: ответ `yes` с `elapsed_time_ms <= 300000` / все участники с `recommendations_requested`; цель ≥70% |

Основной KPI уже настроен в панели по уникальным кодам участников, а не по cookie или PostHog distinct ID. Его знаменатель — коды с `recommendations_requested`, числитель — среди них коды с `recipe_usefulness_answered`, `answer = yes` и `elapsed_time_ms <= 300000`. Если участников пока нет, показатель пустой, а не нулевой. Это сохраняет корректный счет, даже если тест проводят в общем браузере с последовательной сменой кодов.

Дополнительная воронка в панели показывает `recommendations_requested → recipe_opened → recipe_usefulness_answered` с фильтром `participant_code is set`, `answer = yes` и выбором рецепта за 5 минут. Окно воронки — 30 дней, чтобы поздний ответ после готовки не исключался. Она показывает потери по шагам, но может объединять разные коды в одном браузере; для решения о достижении порога 70% используйте только основной SQL-показатель.

## Публикация в GitHub Pages

### 1. Создайте репозиторий

В GitHub выберите **New repository**, задайте имя, например `cookly`, и создайте пустой публичный репозиторий. Не добавляйте README, `.gitignore` или лицензию на этом шаге: файлы проекта уже находятся локально. Публичный репозиторий позволяет пользоваться GitHub Pages на бесплатном тарифе.

### 2. Включите GitHub Pages

Откройте репозиторий → **Settings → Pages → Build and deployment → Source** и выберите **GitHub Actions**. Сборка будет выполняться workflow, а результатом публикации станет содержимое `dist/`. Этот способ описан в [документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

### 3. Загрузите проект

Замените `OWNER` на ваш логин или организацию, а `cookly` — на фактическое имя репозитория:

```sh
git init
git add .
git commit -m "Create Cookly MVP"
git branch -M main
git remote add origin https://github.com/OWNER/cookly.git
git push -u origin main
```

Если `origin` уже настроен, проверьте его командой `git remote -v` и при необходимости замените адрес через `git remote set-url origin https://github.com/OWNER/cookly.git`. Для push потребуется ваша обычная авторизация в GitHub.

### 4. Дождитесь workflow

Во вкладке **Actions** откройте **Deploy Cookly to GitHub Pages**. Workflow запускается после push в `main` и вручную через **Run workflow**:

1. Получает код и настраивает Node.js 22.
2. Устанавливает зависимости командой `npm ci`.
3. Выполняет тесты и production-сборку.
4. Передает `dist/` в GitHub Pages и публикует сайт.

В файле workflow уже заданы разрешения `contents: read`, `pages: write`, `id-token: write`, окружение `github-pages` и последовательное выполнение публикаций через `concurrency`. Если организация ограничивает GitHub Actions, ее политика должна разрешать используемые официальные actions. Если первый запуск произошел до включения Pages, после настройки повторите его.

Для PostHog в репозитории уже заданы следующие repository variables (**Settings → Secrets and variables → Actions → Variables**):

| Variable | Значение |
| --- | --- |
| `VITE_ANALYTICS_ENABLED` | `true` |
| `VITE_POSTHOG_KEY` | публичный Project API Key проекта |
| `VITE_POSTHOG_HOST` | `https://us.i.posthog.com` |

Это именно build-time variables: Vite встраивает их в клиентский bundle. Поэтому сюда нельзя помещать Personal API Key или серверный секрет. Если variables отсутствуют, workflow подставляет `VITE_ANALYTICS_ENABLED=false`, а публикация продолжается без PostHog. Если аналитика включена, но ключ или host не заполнен либо ключ не начинается с `phc_`, этап валидации остановит сборку с понятной ошибкой вместо публикации небезопасно или частично настроенного трекера.

### 5. Откройте сайт

После успешной публикации URL появится в **Settings → Pages** и в результате deploy job. Для обычного репозитория `cookly` адрес будет:

```text
https://OWNER.github.io/cookly/
```

Для специального репозитория `OWNER.github.io` адрес будет `https://OWNER.github.io/`. Фактическая публикация произойдет только после загрузки проекта в ваш репозиторий и успешного выполнения workflow.

### Base path и прямые ссылки

Workflow автоматически передает `VITE_BASE_PATH`: `/cookly/` для проекта `cookly`, `/` для репозитория `OWNER.github.io`. Vite читает переменную через `loadEnv` и использует `base: env.VITE_BASE_PATH || './'`; локальная сборка по умолчанию получает относительные пути. Правила для project sites и корневых сайтов описаны в [документации Vite](https://vite.dev/guide/static-deploy.html#github-pages).

Используется `HashRouter`: путь экрана находится после `#`. Поэтому обновление страницы рецепта и открытие скопированной ссылки работают на статическом хостинге без серверной настройки маршрутов. Удалять `#` из ссылки не нужно.

Для проверки сборки с путем проекта в PowerShell:

```powershell
$env:VITE_BASE_PATH = '/cookly/'
npm run build
npm run preview
```

## Ручная проверка сценария

1. Добавьте курицу, картофель, лук, помидоры и сыр; оставьте время «Неважно».
2. Убедитесь, что повторный ввод продукта не создает дубликат.
3. Нажмите «Что приготовить?» и дождитесь результатов; должно быть минимум три релевантных блюда.
4. Откройте рецепт, проверьте наличие количества ингредиентов, разделения на доступные и недостающие продукты и подробных шагов.
5. Нажмите «Буду готовить» и проверьте подтверждение.
6. Вернитесь к форме поиска и обновите страницу: временный список продуктов и лимит времени должны сброситься. Отдельно откройте «Мой холодильник» и убедитесь, что его продукты восстановились.
7. Проверьте пустой список, очень короткий лимит времени, удаление и очистку продуктов.
8. Повторите на ширине 320–430 px и на широком экране; проверьте отсутствие горизонтального скролла и работу клавиатуры.
